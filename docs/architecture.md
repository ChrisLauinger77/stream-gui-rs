# Stream GUI RS architecture through Phase 5

```text
React (browsing + Watching + settings, public DTOs only)
    ↓ typed Tauri IPC
Rust backend
    ├── Twitch device authorization / validation / refresh
    │      └── CredentialVault → platform CredentialStore
    ├── Browsing queries / safe application DTOs
    │      └── Helix endpoint methods / typed models
    │      ├── bounded cache / pagination / ID batching
    │      └── shared Twitch HTTP pool / rate coordinator
    ├── followed-stream monitor → native notifications / tray / window lifecycle
    ├── versioned global/channel settings + trusted browser chat
    └── Streamlink discovery / probe / session supervision
            ↓ native process + argument array, never a shell
        Streamlink
            ↓ default / mpv / VLC / custom player
        external player
```

The application identity is `io.github.stream-gui-rs`; Tauri derives application directories from it. Secure credentials use the separate service `io.github.stream-gui-rs.oauth`, keyed by the public Twitch client ID. The pre-release rename intentionally starts with new settings and a fresh login. Twitch/Helix modules and IPC contracts retain their existing names and ownership.

## Ownership

`domain` holds errors, request DTOs and the service coordinator. `streamlink`, `twitch`, `twitch_http`, `helix`, `config`, `credentials`, `diagnostics`, `monitor`, and `platform` have no Tauri dependency. `desktop` composes services, resolves the platform application directory, opens the window, and handles shutdown. `commands` contains only adapters. The optional `desktop` Cargo feature allows backend tests without WebView libraries.

The frontend shell and authentication hook live in `app`; `browse` owns view navigation, query snapshots, shared stream/image presentation, search and details; `lib` owns generated DTOs and typed IPC; `styles` owns theme tokens. `playback` holds the snapshot/request hook and quality presentation; `features` holds the shared Watching and playback settings components, plus authentication diagnostics. React state contains only UI inputs and backend snapshots. There is no frontend OAuth client or token persistence. The monitor, auth and process tasks remain with their Rust services independently of webview lifetime. Native notification/tray adapters live under `desktop`.

## IPC

Rust DTOs derive `TS` and generate `src/lib/generated.ts`. A checked-in equality test enforces the contract. `src/lib/ipc.ts` is the only frontend `invoke` entry point and accepts a closed set of named operations and typed request objects. Rejections carry `{code, message}`. External provider bodies never become errors or logs.

Commands cover backend diagnostics, probe/save, global settings get/update, channel override get/update, restricted browser chat, player discovery, launch, stop, generation-checked restart, session snapshots, auth status/login/cancel/logout/validate/refresh/account, opening the current Twitch verification link, the eight browsing operations listed below, and `desktop_status`, `pause_monitor`, `resume_monitor`, `request_notification_permission`, `acknowledge_desktop_action` and `quit_application`. No frontend-selected shell, arbitrary argv, generic filesystem API or arbitrary browser URL is exposed. Selecting a custom Streamlink executable is an intentional local trust decision: version probing is validation, not executable sandboxing.

The main window has an explicit command allowlist generated by Tauri's application manifest. Remote origins get no capability. Production CSP blocks third-party scripts, direct web API connections, frames, and form submission. Only Rust contacts Twitch OAuth and Helix. Safe account and browsing DTOs permit HTTPS images from `static-cdn.jtvnw.net`; the CSP allows only that image origin in addition to local assets. The browser-opening command accepts no URL argument and checks the provider's HTTPS Twitch activation URL.

## Streamlink sessions

The reviewed Phase 0 `Supervisor` is the sole process registry. Phase 3 adds typed settings/command construction, identity resolution and restart generations to it; it does not introduce a second process owner.

```text
Watch(broadcaster ID, public auth-session ID, optional quality policy)
  → bounded service-owned playback operation
  → uncached Rust Helix live-identity lookup for that exact auth session
  → Rust resolves global preferences < channel overrides < request quality
  → native executable discovery/version probe
  → LaunchSpec (resolved paths, trusted identity, immutable effective preferences)
  → pure CommandSpec (executable + argv vector, no process creation)
  → existing Supervisor → Streamlink → external player
```

The login alone constructs `https://www.twitch.tv/<login>` after ASCII channel-name validation. Display names, titles and categories are session metadata and never become command arguments. The service rechecks authentication after probing. Twitch stream ID, broadcaster ID, login and display name remain distinct. Existing session restart retains that identity without a new Helix lookup; it can therefore report offline or renamed-channel failure through Streamlink diagnostics. It never resolves a new account on behalf of an old request.

Discovery tries absolute PATH entries and common platform locations: Linux `/usr/local/bin`, `/usr/bin`, `/bin`, `~/.local/bin`; macOS additionally `/opt/homebrew/bin` plus mpv/VLC executables in system/user Applications bundles; Windows native `.exe` names under PATH, Program Files and Local App Data/Programs. A custom absolute path is the escape hatch. No interpreter/profile/download framework is involved. Explicit paths preserve the user's spelling/symlink in settings and resolve their current target for each use. Directories, non-executable Unix files and Windows script wrappers are rejected. Player discovery is independently testable without Tauri.

The version probe concurrently drains both pipes with bounded capture and a five-second deadline, killing/reaping on timeout. Production playback requires Streamlink 8.0+. The base argv is `--no-config --no-plugin-sideloading --loglevel info --player-verbose`, followed by optional player/quality flags and `--`, canonical channel URL, quality selection. `Command::new` receives the executable path separately; no shell command is composed. The only prototype URL/quality launch adapter is retained for Phase 0 native contract tests and is not reachable through IPC. OAuth tokens are not passed in argv, environment additions or configuration files.

| Policy | Positional selection | `--stream-sorting-excludes` |
| --- | --- | --- |
| Source | `best` | omitted |
| High | `high,best,best-unfiltered` | `>720p30` |
| Medium | `medium,best,best-unfiltered` | `>540p30` |
| Low | `low,best,best-unfiltered` | `>360p30` |
| Audio | `audio,audio_only` | omitted |

These follow the original app's policy model using current Streamlink syntax. The final unfiltered fallback deliberately permits a rendition above the nominal cap when needed. There is no rendition-discovery request/UI or automatic observer-driven relaunch.

Player modes are default (delegate discovery to Streamlink), mpv, VLC and custom. mpv adds `--keep-open=no --quiet`; VLC adds `--play-and-exit`, with `--no-one-instance` only on Linux/Windows because native macOS VLC does not support that option. Additional arguments are a bounded vector of literal strings, not shell text. Each entry has formatting braces doubled, is POSIX-single-quoted with embedded quotes escaped, and is joined for Streamlink's second parsing boundary (Formatter followed by `shlex.split`, including on Windows). An owned `{playerinput}` is always appended so a literal user string containing that text cannot suppress stdin. Executable paths are separate unquoted argv values. The supported transport is Streamlink's normal player stdin only. See [validation and upstream references](phase-3-validation.md).

Each session has a stable UUID, generation, trusted metadata, selected policy, immutable effective-settings snapshot, optional chat error, process phase, timestamps, optional typed failure and bounded logs. A successfully spawned process is `running`; restart preparation is `starting`, and cleanup is `stopping`. Natural success or requested stop ends in `exited`; unexpected process failure ends in `failed`. Nonzero exit before three seconds is classified `startup_failed`, later exit `streamlink_exited`. This timing is diagnostic only: neither it nor `Starting player:` proves video rendering.

One task owns each child and two concurrent readers drain stdout/stderr. Stop signals under the registry lock, releases it before waiting, and is idempotent for retained IDs. Restart accepts the observed generation, reserves the same session, reaps the old child/readers, resolves current settings and then spawns the replacement. Stale generations and overlapping restart attempts are rejected. An external Stop increments a cancellation revision, preventing a pending restart from spawning; shutdown closes the registry. A dropped IPC caller cannot abandon production launch/restart work because the service task owns it. Dropping a lower-level restart future also releases its reservation. Replacement retains metadata/ID and bounded diagnostics with a restart marker; it never overlaps the prior generation.

Eight active/reserved sessions, eight outstanding playback operations and sixteen retained snapshots bound capacity. A terminal history entry cannot restart past active capacity. Only unreserved terminal snapshots may be evicted; unknown/evicted IDs return `not_found`. Spawn failures before a first child create no session; restart failures retain the session and a safe diagnostic. Starting channel A does not stop B. Requests always target explicit session IDs.

Per session, 200 log entries are retained. Individual lines are bounded to 2,048 input bytes; oversize lines are omitted while pipes continue draining. Invalid UTF-8 is replaced, terminal control characters are stripped, and common credential-related lines are suppressed. Logs are React text, available only within that session, and never persisted. An untrusted custom executable can still output arbitrary sensitive content; the filter is not a universal secret detector.

Unix children use a separate process group. Windows children start suspended and enter a kill-on-close Job Object before their primary thread is resumed, preserving the reviewed ToolHelp adapter and hidden-console behavior. Stop and normal parent exit clean up owned descendants and reap the direct child; readers are cancelled if inherited pipes remain open. Intentionally detached/custom external players are outside that ownership boundary.

Navigation, webview reload and Twitch logout do not stop already-owned sessions. Restart and Stop remain available after logout; new browsing launches require an authenticated session. Main-window Close defaults to the existing shutdown path. With opt-in background close, it hides the window when a usable tray exists, otherwise minimizes it. Normal minimize is unchanged. Explicit Quit always enters the same shutdown coordinator: cancel/join the monitor, close service gates, signal sessions, cancel pending restart, await sessions/probes/authentication/chat cleanup, drain native notification ownership, then exit. Tray and main-interface Quit labels state the active playback count that will stop. `kill_on_drop` and group/job ownership are backups. An uncatchable Unix app kill cannot guarantee cleanup; no process-recovery daemon is implemented.

## Authentication and settings

One Rust service serializes credential restoration, device polling, validation, refresh, and logout. An auth-only async mutex protects operations spanning HTTP and secure-store writes; it is independent of the playback locks. A separate watch snapshot makes `auth_status` immediately readable during network or keychain waits. Explicit cancellation signals the pending device request before waiting for the credential owner; late completion cannot reauthenticate after cancellation or logout.

Auth operations belong to service tasks, not to the lifetime of an IPC caller. Dropping a caller cannot abandon a token rotation or let a queued keychain write land after logout. Concurrent explicit validation/refresh calls share completed operation revisions; concurrent Helix 401s verify the original session before comparing credential generations and sharing one refresh. An internal access lease carries a secret token plus account/session/generation identity and cancellation; it is never serializable. Logout/revocation/shutdown cancel leases. A later login has a new session identity, so it cannot reuse an old account's cache entries or supply a replacement lease to an older logical Helix operation.

The Rust startup configuration resolves an explicit `TWITCH_CLIENT_ID` developer override before the public ID embedded from `TWITCH_CLIENT_ID_BUILD`. Missing or invalid startup configuration is an error before secure storage is opened. `build.rs` requires an embedded ID for non-debug Cargo profiles and Tauri `custom-protocol` builds, including packaged debug builds; a runtime override cannot satisfy that requirement. The public ID may be present in the binary, while OAuth token persistence remains exclusively in the platform credential store. See [configuration precedence and build commands](authentication.md).

Startup and hourly validation run in Rust independently of the webview. Identity, client ID, scopes, and expiry must validate before the account is exposed. Refresh preserves the validated account ID. Transient validation errors hide identity and retry after 60 seconds. Refresh occurs at known expiration, recoverable access-token validation rejection, or a Helix 401, and never blindly retries a one-use refresh token. Newly issued tokens are validated without recursive refresh. Secure deletion must be confirmed by an absent-entry read before rotation is dispatched. Normal shutdown cancels device polling, rejects queued/new auth work, and waits for an active rotation and secure-store write; process shutdown proceeds concurrently.

`CredentialStore` remains the Rust-only storage interface. `CredentialVault` serializes its blocking OS calls on blocking workers. Desktop uses Keychain, Credential Manager, or Secret Service; memory storage is for deterministic tests. A process-held filesystem lock prevents two instances using this application's configuration directory from rotating the same entry. Credentials are a single versioned secure-store record, separate from settings. There is no insecure fallback. Token types have no Debug/IPC serialization and owned token buffers zeroize on drop; networking/OS libraries may have their own temporary copies. See [authentication](authentication.md) for rotation and storage tradeoffs.

`TwitchHttp` owns one reqwest connection pool shared by OAuth and Helix. The Helix client owns its shared rate coordinator and bounded cache, with typed endpoint methods and no arbitrary endpoint/URL IPC. The cache has distinct live/metadata/category lifetimes; stale results and incomplete batches are explicit. Foreground callers control each pagination step; the monitor deliberately assembles one bounded followed-live scan. A small internal clock helper accumulates elapsed time from monotonic and wall clocks for authentication, cache age and rate resets. System sleep counts even when monotonic time pauses; backward wall adjustments cannot rewind freshness or extend an observed deadline. Short waits remain Tokio timers. See [Helix contracts](helix.md).

React holds UI inputs and safe backend snapshots. It reconstructs auth from status/account commands after reload and discards late account responses after logout. The shell polls auth at most once per second after completion, reads account details once per public auth-session generation, and does not reload account state on navigation. The application playback hook independently polls Rust session snapshots at most once per second after completion, including when Watching is closed. A request revision discards polls predating a completed action. Reload reconstructs sessions from Rust; React only owns pending-request guards, panel visibility and a draft restart quality. Failed account reads retry after 60 seconds. Pending auth, cancellation, probe/launch, and each session's Stop have separate guards; the backend remains authoritative. There is no frontend Twitch API client or authoritative query cache.

`SettingsStore` owns strict version 4 JSON: a `version`, typed global `settings`, and a sparse `channelOverrides` map. Globals contain `streamlinkPath`, player mode/optional executable/literal arguments, `defaultQuality`, `automaticChat`, `theme` and typed `background` preferences. This application's versions 1, 2 and 3 migrate in memory, preserving existing playback/channel/theme values and defaulting new background preferences off; only a successful save writes version 4. The old webview-only appearance preference is not imported and starts at System. No legacy GUI or prior identity namespace is imported.

The directory comes from Tauri's `app_config_dir()` (XDG configuration on Linux). Reads/writes are bounded to 256 KiB and 1,000 channel records. A document mutex serializes snapshots and updates; global saves preserve channel records, and path probes update only the path. Blocking writes use a temporary file in the same directory, sync it, then atomically replace the destination. Failed persistence leaves memory and the original file unchanged. Malformed JSON, invalid enums/paths/IDs and unknown schema fields/versions fail safely; desktop setup reports the categorized error and exits without panicking or replacing the file. Explicit Streamlink paths are probed and require version 8+ before save, and player paths are resolved/validated before save.

Channel records use stable positive decimal broadcaster IDs (at most 32 ASCII digits), never login/display names. Each independent `quality`/`automaticChat`/`notifications` field is nullable: null inherits, while false explicitly disables the respective boolean preference. Rust resolves notification overrides against the global notification default separately from playback configuration. An entirely inherited record is removed. These are local device preferences shared across signed-in accounts, not account-specific Twitch data. Channel settings cannot grant playback or chat authority; those operations separately validate the current authentication session and trusted identity.

Rust alone resolves global preferences, then channel overrides, then optional request quality into `EffectivePlaybackSettings`. Channel previews return this same resolution. `LaunchSpec`, command construction and the retained session snapshot carry a copy; changing preferences cannot modify a running process. Restart retains the session identity, reaps the old generation and resolves current preferences; the UI sends null by default or an explicitly selected quality. Frontend drafts never independently resolve inheritance.

The narrow `channel_settings` and `save_channel_settings` commands return the selected channel's overrides, global defaults and effective preview. There is no arbitrary settings-key API, filesystem destination or token field. Global and channel updates are separate typed operations.

Successful custom-path probes save the validated absolute path selected by the user, preserving stable symlinks across package upgrades. Discovery resolves its current target for each probe and launch; the resolved path is diagnostic output, not the persisted preference.

## Shell, settings and navigation

The compact sidebar exposes Following, Live, Categories and Search; account controls remain in the top bar. A small in-memory route union adds category and channel detail routes. No browser URL router or new component framework is needed for this desktop application. A bounded twelve-entry Back stack records route, scroll position and focused item; native buttons provide keyboard activation and visible focus. The minimum native window is 620 × 600; grids adapt and navigation becomes horizontal at smaller preview widths.

System/Light/Dark themes use CSS variables and a Rust-persisted preference. The appearance hook listens to `prefers-color-scheme`, updates root theme/resolved-theme state and native control color-scheme, and removes its listener on unmount. System follows the preference exposed by the native webview; no desktop-specific theme integration is assumed. No account, query, cursor, credential or preference authority lives in localStorage. `DeveloperTools` retains the old screen and process actions, unmounting the browsing shell while open. Stream cards and live channel rows/details now provide a separate keyboard-accessible Watch action. Watching and playback settings are compact, scrollable panels; opening either leaves the browsing workspace mounted. Normal UI renders fixed typed-error messages rather than arbitrary backend error text.

Settings has Playback, Streamlink, Player, Appearance, Background and Shortcuts sections with one visible form section. A draft survives section navigation, Save accepts the validated backend snapshot, Cancel restores it, and closing the panel discards unsaved changes. A successful Streamlink test separately saves only its path. Channel details provide independent inheritance selectors and manual chat. Loading/error/pending states remain explicit; late channel responses are discarded across navigation, account changes and global-save revisions.

Focused keyboard handling is a DOM listener in the application shell, not an OS hotkey. Control+K/1/2/3/4/comma/R selects Search/Following/Live/Categories/Watching/Settings/Refresh on Linux and Windows; macOS uses Command. Back is Alt+Left (also Command+[ on macOS). Navigation reuses the existing bounded route history and focus restoration; Search focuses its input. Refresh delegates to the current browsing control. Inputs, textareas, selects, editable content, composition, repeated keys and modal dialogs suppress shortcuts. Settings lists the platform-appropriate reference; developer diagnostics does not install a second shortcut map.

## Restricted external browser chat

`open_channel_chat` accepts only a broadcaster ID and public auth-session marker. Helix resolves a fresh user login bound to that exact session, including offline users; a mismatched/invalid response fails. The service rechecks the lease before dispatch. `ChatTarget` validates the login and constructs only `https://www.twitch.tv/popout/<login>/chat`. React/provider metadata cannot supply a URL, executable, browser arguments or token.

Automatic chat runs in Rust once after a successful launch or explicit restart, using that run's immutable effective preference and retained trusted login. Existing session restart remains possible after logout and does not re-resolve an old stream under another account. A failed browser dispatch records a safe generation-checked `chatError` without failing or hiding playback. Navigation and snapshot polling never open chat.

`BrowserChat` has four bounded request slots and serializes native dispatch. A service-owned task retains the blocking call if an IPC caller disappears; queued requests recheck cancellation/shutdown before dispatch, and shutdown waits for the in-progress native opener. Linux uses GIO's default URI handler with a private worker context, awaiting asynchronous dispatch and allowing GIO to reap short-lived browser launchers. This also fixes the pre-existing Linux authentication browser opener's unreaped launcher. macOS/Windows retain the existing `webbrowser` adapter. GIO was already in Tauri's GTK dependency graph; it is now an explicit optional Linux desktop dependency, with no newly resolved package. See [GIO dispatch semantics](https://docs.gtk.org/gio/type_func.AppInfo.launch_default_for_uri_async.html).

The authentication command still accepts no arguments and opens only its validated activation URL. Both commands use the same internal native adapter; no generic URL IPC is introduced. Browser pages use the browser's own Twitch session, and browser lifetime is independent of owned playback. Neither normal tests nor the isolated Linux browser regression open a real browser.

## Browsing IPC and DTO boundary

| Command | Request | Response |
| --- | --- | --- |
| `list_followed_streams` | `BrowseRequest` | `PagedResult<StreamSummary>` |
| `list_followed_channels` | `BrowseRequest` | `PagedResult<ChannelSummary>` |
| `list_streams` | `BrowseRequest` | `PagedResult<StreamSummary>` |
| `list_categories` | `BrowseRequest` | `PagedResult<CategorySummary>` |
| `list_category_streams` | `EntityRequest` | `CategoryDetails` |
| `search_channels` | `SearchRequest` | `PagedResult<ChannelSummary>` |
| `search_categories` | `SearchRequest` | `PagedResult<CategorySummary>` |
| `get_channel` | `EntityRequest` | `ChannelDetails` |

`BrowseRequest` carries a public `sessionId`, an optional cursor, and an explicit refresh flag. Entity/search requests add an ID/query, never an arbitrary endpoint or URL. `AuthStatus.sessionId` is a public generation marker, not a credential or authority grant. Rust obtains an authenticated lease for that exact session before querying and pins every enrichment/retry to it. Logout or a later login cancels the original lease. React keys its whole browsing workspace by this marker, clearing all navigation snapshots even when the same user logs out and back in.

Thin command adapters acquire one of eight browse permits and invoke `helix::browse`. This bounds outstanding searches and rate-limit waiters without queuing unlimited IPC work. Authentication and process management have independent capacity. Query DTOs distinguish stream ID, broadcaster ID, login and display name. Optional category/description/language/image fields are explicit; DTOs exclude raw provider bodies, tokens, email and private account metadata. Errors are typed codes rendered through fixed user-facing messages.

Following channels enriches only the requested page with one user metadata batch and at most one live-status batch. Fresh positive live matches from the first followed-stream page reuse the existing backend cache; unseen IDs are still queried, since omissions in a paginated response never prove offline status. Explicit refresh bypasses live reuse. A successful complete stream response can establish offline state; network failures or incomplete responses produce unknown status and warnings. Partial metadata failure preserves follow identity and follow date. Authentication failures remain terminal. Channel details use the same distinction.

## Freshness, pagination and rendering bounds

The existing Rust cache remains authoritative: 15-second live data, 300-second user metadata, 3,600-second category metadata, at most 128 entries/8 MiB. Cross-view reuse uses the same session-scoped query keys and TTL checks, with no second cache. Refresh bypasses live/query cache entries; long-lived profile/category enrichment may still use its own fresh metadata entry. Result DTOs report network/cached/stale state, maximum source age and partial-detail warnings.

Each list command requests 30 items and returns an explicit cursor. React requests another page only on Load more, deduplicates by the correct entity ID, rejects repeated cursors and retains at most 10 pages/300 items per view. Refresh starts that view over. Its `ViewMemory` retains at most twelve view snapshots for navigation; it has no TTL, background refresh or independent freshness rules. Restored and accumulated snapshots are labeled Previous results; failed refresh keeps existing data with an update-failed message. Only Rust can return a fresh/cached result. Phase 2 does not automatically fall back to expired backend entries.

Search debounces for 350 ms, trims input, ignores empty queries and separates channel/category cursors. Editing the query immediately unmounts older results, so a late response cannot replace the new query even during debounce. Superseded IPC calls may finish under the existing HTTP/rate bounds and eight-query capacity; account cancellation terminates them at the backend. Request generations and unmount guards also protect refresh, pagination and account reads.

Shared `StreamList`/`StreamPreview`, category artwork and channel rows keep presentation consistent. Rust permits only Twitch CDN HTTPS image URLs and substitutes bounded dimensions (480 × 270 preview, 144 × 192 artwork, compact profiles). React loads images lazily, keeps aspect ratios reserved, uses empty alt text alongside labeled controls, and displays placeholders on failure. No image proxy, original-resolution fetcher or virtualization layer was introduced. Loading, empty, missing permission, unavailable, offline and network-error states remain distinct.

See [Phase 5 validation](phase-5-validation.md) for background lifecycle and native-adapter evidence, [Phase 4 validation](phase-4-validation.md) for historical settings/chat/shortcut and native Linux evidence, [Phase 3 validation](phase-3-validation.md) for preserved playback history, and [Phase 2 validation](phase-2-validation.md) for the preserved browsing contracts.

## Background monitor and native lifecycle

`Services` owns one `Monitor` task alongside its existing `AuthService`, shared `HelixClient`, settings and sole playback Supervisor. `desktop` starts it once; React routing, visibility and reload cannot start or stop it. Auth snapshots expose only the internal session marker and cancellation token to the monitor. Every scan pins that session through pagination, retries and lease reacquisition. Temporary auth unavailability pauses observation and requires a quiet recovery baseline, but retains deduplication while the original session token remains uncancelled. Logout/session cancellation or replacement drops that session's transition history. New login starts quietly, including re-login to the same user, and old notification targets remain cancelled.

Persistent settings are `monitoringEnabled`, `notificationsEnabled`, `closeToBackground` (all false by default) and `intervalSeconds` (60, 120 or 300; default 60). Pause is ephemeral: it cancels polling and outstanding notification actions without logging out or stopping playback, lasts until Resume or restart, and resumes with a quiet baseline. Changes to background preferences also cancel/rebaseline. Other global settings saves do not reset monitoring.

The monitor runs one complete bounded scan per interval, with 0–10 seconds of per-process jitter and a 45-second deadline. Ordinary scans share fresh Following pages. Every quiet baseline instead uses `CachePolicy::Refresh` for all pages, fetching after the new observation boundary without invalidating unrelated cache entries. All scans yield scarce request capacity/budget to interactive work; [Helix contracts](helix.md#background-followed-live-scans) specify the limits. Incomplete scans are errors, never a truncated baseline. Recoverable errors retain a marked previous count and back off exponentially from the chosen interval, capped at 900 seconds plus jitter. A successful recovery is a quiet baseline. There is no unbounded polling log: the snapshot carries the current phase, error category, retry delay, previous/live count and notification-delivery failure flag.

Transitions use `(broadcaster ID, Twitch stream ID)`, independent of names or titles. Initial streams enter history silently. Two complete missing scans confirm absence for the live count; failures/incomplete scans never count as absence. Reappearance of the same stream ID remains suppressed even after confirmed absence. A new stream ID is a new event. History is bounded to 16,000 entries; reaching capacity discards history and establishes another quiet baseline. Deduplication survives frontend reload and retries, but intentionally does not persist after app exit. At most ten eligible notifications are dispatched per scan; other observed events are marked seen and suppressed, not replayed later.

The existing suspend-aware `Clock` drives scheduling. A gap over ten seconds between one-second heartbeats means suspend or a long scheduler stall: refresh the quiet baseline. During an in-flight scan, the heartbeat can cancel the scan; result acceptance also checks the last heartbeat before overwriting the elapsed boundary or accepting transitions. A response that completes before the first post-resume heartbeat is therefore discarded too. Recovery fetches a quiet baseline without clearing shared live cache pages. Ordinary slow scans may continue up to the scan deadline while heartbeats run. Auth validation and rate/cache expiry keep their existing suspend-aware behavior; the monitor never bypasses an auth lease.

Native notifications use a bounded 32-command queue and one worker. OS notification records are capped at 32 and retired on cancellation, expiry (15 minutes), applicable close/click events, or shutdown. Every dispatch and activation rechecks auth/monitor cancellation. Text is control-stripped and bounded; markup/XML is escaped where needed. No remote image retrieval is required. Failure never stops Twitch monitoring. Permission is exposed separately and is requested only by the explicit UI action.

- Linux uses GIO and `org.freedesktop.Notifications`, detects advertised action support, and reports OS-managed delivery. `desktop-entry` matches the packaged `Stream GUI RS.desktop` basename. Notification-server owner changes clear old action IDs. A missing server reports unavailable and is checked again later.
- Windows uses WinRT toast APIs with `io.github.stream-gui-rs` and a balanced worker apartment. Banner timeout retains the notification and its activation target for Notification Center. A running COM activator is registered under the same AUMID's per-user `CustomActivator`; both banner and COM callbacks resolve a random opaque ID in one bounded registry and consume it once. Native callbacks cannot supply channel IDs, URLs or commands. At most 32 targets/handler sets live for 15 minutes, including time asleep. User dismissal, activation, cancellation, expiry or Quit removes handlers and the exact tag/group history entry. A session-local identity guard prevents a second instance from replacing the route or clearing the first instance's notifications. Quit revokes the COM factory and activation route; no executable/cold-launch registration is added. Startup removes orphaned history after acquiring that identity. OS display identity and notification preferences remain. Installed application testing is required; delivery/activation from a bare portable executable is not promised. Failed native delivery is safely categorized.
- macOS uses UserNotifications with the matching app bundle ID, explicit authorization, bounded retained requests and a native delegate. A bare executable is unavailable. Permission checks remain asynchronous and bounded while the user considers a prompt; the worker has short-lived autorelease pools.

Tauri's tray API provides Show, Hide, Pause/Resume, Watching count and Quit. A one-second native presentation loop reads Rust snapshots; it owns no monitoring or playback state. Linux checks the indicator library before calling the dynamically loaded API, reads the StatusNotifier watcher’s registered-host property (watcher presence alone is insufficient), disables Hide without a host and restores a hidden window if the host disappears. Tray failure leaves a reachable minimized window for background close. Menu actions are the portable interaction contract; pointer-event parity is not assumed.

Notification activation restores/focuses the window and retains one safe `DesktopAction` in Rust until acknowledged. The latest action replaces an earlier unhandled action. Channel targets contain trusted broadcaster and auth-session IDs, never arbitrary URLs. `desktop_status` removes obsolete-account targets. React polls this small native snapshot every two seconds, guards late polls, reconstructs after reload and navigates once to the matching workspace; clicking does not launch playback. Watching tray actions use the same snapshot path and work after logout. Quit always uses the existing shutdown coordinator.
